## Recommendation and one user decision

Approve a **reference-faithful pending-selection contract**: saving an override or explicit default reset records durable intent; it does not rewrite the identity of an active attempt. Backplane alone determines execution/adoption boundaries. A normal newly admitted run can use the saved selection; the complete end-state also permits adoption within the same user turn at a native replay-safe recovery/compaction boundary, as the reference does. Neither “immediate switch” nor “always next turn” is the contract.

**Decision for the user:** approve the full pending-selection and metadata-writer contract below, or request changes to this proposal. Ordinary next-run adoption may be a verified implementation stage, but it cannot replace the reference recovery/compaction end-state or close P5.

## What the sources establish

1. Fixed OpenClaw `488631c`, `src/agents/tools/session-status-model.ts:60-181`, persists selection intent and requests `markLiveSwitchPending: true`. `src/sessions/model-overrides.ts:79-145` removes overrides for an explicit default, marks its source as default, and can clear stale runtime-derived model fields. Absence of an override plus pending therefore means a deliberate reset, not no selection request. `tools/common.ts:117` treats trimmed blank and case-insensitive `default` as reset; omitted `model` is observation only.
2. `src/agents/live-model-switch.ts:93-147,168-285` compares the selected identity with the actual identity and only clears the selection it observed. `embedded-agent-runner/run/attempt-recovery.ts:300-335` checks pending selection and runtime replay safety. `attempt-normalization.ts:309` additionally requires no outbound delivery, deterministic approval prompt, last tool error, tool metadata, or assistant text. Thus a tool-triggered request does not inherently switch the very next HTTP request. The reference's complete recovery behavior is more specific than a generic per-request model lookup.
3. Current `Worker.Config.do_switch_model/3` (`apps/synapsis_agent/lib/synapsis/session/worker/config.ex:305`) validates/preflights complete history synchronously and writes a whole session map. `Worker` (`worker.ex:526-555`) allows this only while idle, then changes its cached provider/model and broadcasts `model_switched`. There is no separate durable pending/default intent or observed attempt record.
4. `Session.to_meta/2` (`apps/synapsis_data/lib/synapsis/session.ex:38-49`) serializes a fixed field allowlist; `from_meta/1` also drops unknown fields. Adding a raw metadata field without changing writers would not preserve it. Current `provider`, `model`, and config `provider_id`/`model_id` express the selected identity, not proof that a provider attempt occurred.
5. `Worker.Runtime.start_turn/4` and `prepare_selected_turn/5` prepare a run, compact before admission, and publish the input via `Store.commit_turns/4`. `SessionAdapter` (`session_adapter.ex:1472`) freezes provider config/request options into native run options. `ProviderAdapter.relay/6` reads that context and delegates to the existing provider facade. Backplane creates attempt IDs and starts effects (`conversation.ex:1723`); the host adapter does not own execution sequencing.
6. Concord supports `KV.get(..., engine: :turso, metadata: true)` with `Record.mod_revision`, `KV.compare_and_swap/3`, and `Turso.txn/2` revision predicates. `Turso.replace_prefix/3` supports comparisons and atomic replacement plus metadata. Read/write calls take a finite remaining timeout; work already admitted can complete after timeout. A timeout is not proof of rollback. Historical #107 is not a reason to prohibit all revision-based work now.
7. A material capacity distinction remains: `Concord.put_many/2` (`deps/concord/lib/concord.ex:567`) emits unconditional puts; it does not implement a compare option. Generic transactions have 128 operations, 64 comparisons, and a 1,000,000-byte envelope (`command_schema.ex:8-16`). Existing `commit_turns/4` uses the larger batch contract. Simply replacing it with a transaction silently narrows accepted history sizes. `replace_prefix` has a larger envelope but replaces a prefix; using an artificial prefix or the metadata-key prefix as an append workaround is not proposed. Generic session-scoped values can share that prefix, so a prefix deletion is not an exact-key append primitive.

## Alternatives

| Approach | Result and tradeoff |
| --- | --- |
| Extend idle immediate switching | Smallest behavioral change, but the native tool runs during an active turn and cannot obtain reference pending/reset behavior. Does not solve competing full writers. Reject. |
| Pending intent, adoption only at fresh native admission | Implementable ordinary slice with existing admission/provider adapter boundaries. Preserves active requests, supports normal restore, but permanently differs from reference recovery/compaction timing if accepted as the final product. |
| Pending intent, native safe-boundary adoption | Recommended end-state. One durable selection record and native execution authority; full reference timing requires a qualified native boundary. More integration work, with the two technical gates explicitly retained. |

## Public contract and persisted representation

Selection mutation is explicitly opt-in through `Agent.config.session_model_selection_enabled = true` (default false). Selection of the existing status tool alone does not enable mutation. With the flag absent/false, preserve the current revision-1 read-only schema and behavior. With the flag true and the status tool explicitly selected, construct the mutation-capable revision-2 descriptor with non-read-only safety metadata and the corresponding selection-write grant; omitted `model` still classifies as `session.status.read`, while override/reset classifies as a selection-write action for the exact target session. The existing admission/permission machinery must enforce both classifications; the opt-in flag does not bypass it. Do not enable this variant unless that public admission contract is established. The ordinary Agent configuration UI exposes the opt-in explicitly and defaults it off; no saved Agent is automatically changed.

Retain exact persisted session UUID targeting and the current `source: auto/live/durable` observation semantics. Add optional `model` to native `session_status`: omitted reads; trimmed blank or `default` resets; a model reference requests an override. Initial exact `provider/model` resolution and unqualified model resolution use existing configured providers/models, with current override provider or the agent default as the unqualified base. Do not invent an alias registry or claim OpenClaw plugin/alias resolution parity. Selecting the resolved configured default normalizes to default mode, consistent with the reference. The configured default is resolved from the session's configured Agent and its existing tier/default rules, explicitly excluding session override/cached model fields.

Return a bounded `model_selection` object alongside existing status fields:

- `request_id`, `mode: override|default`, `requested` (canonical provider/model or null), `resolved` (the selected target at this observation), `changed`, and `pending`.
- `active_attempt` only from validated live native attempt observation: provider/model plus run/incarnation/attempt identity. Idle has no active attempt.
- `last_attempt` is explicitly historical, including in durable output; restored metadata never proves a live attempt.

`changed` means a different selection intent was durably committed; it does not mean an HTTP attempt switched. Equal normalized intent is a no-op. Successful mutation waits for the persistence acknowledgement; before that it is not accepted. A newer request may supersede the returned request before the caller next observes status. `source` selects the observation source, not a weaker mutation path.

Proposed additive fields in the existing metadata record (names are proposed, not existing):

| Field | Owner / invariant |
| --- | --- |
| `model_selection` | Selection command service: `{version: 1, request_id: UUID, mode, override}`. Override includes the existing configured stable IDs when available and canonical provider/model. Default mode has no pinned override. |
| `model_adoption` | Native observation projection: last confirmed request ID, resolved identity, and native attempt identity. Never authored by selection commands or inferred from boot/config resolution. |
| existing `provider`, `model`, config `provider_id`/`model_id` | Compatibility projection of selected identity, not actual execution. In default mode the identity is a refreshable projection; it cannot pin resolution to a former override. |
| other config, title, debug, agent, status, timestamps | Existing domain owners, changed through field patches only. Unknown metadata/config keys survive unrelated mutations. |

Pending is derived from selection versus confirmed adoption, including resolved default identity; it is not independently cleared by arbitrary writers. A new request ID prevents an acknowledgement for request A clearing request B even when both choose the same provider/model. A matching attempt does not consume a later request by identity alone. Default resolution is refreshed at native adoption boundaries, so a default-config edit is not mistaken for a permanently pinned reset target.

Old records without these fields retain their existing pinned selection behavior. Do not infer historical override-versus-default intent or actual execution. Materialize a versioned selection when the user first changes it; new sessions can record whether selection was explicitly supplied. Preserve existing provider/model compatibility fields. No bulk migration or rewritten transcript is required. `Session` encoding/decoding must carry the new fields, but raw field-patch merging remains mandatory to preserve unrelated/unknown data.

The existing UI/`Sessions.switch_model/3` writer must join the same selection command path, not keep a second whole-map writer. Its idle eligibility and legacy `:ok` facade can remain for this slice, but `:ok` means committed selection; immediate attempt adoption must not be implied. Presentation should identify pending selection where currently claiming an effective switch. Other native tool behavior, usage/cost, new aliases, state-event API, children with borrowed session identity, and authorization policy expansion are excluded from this design.

## Writer boundary: required together, not optional cleanup

`synapsis_data` remains the only Concord access owner. Add data-only snapshot and typed field-patch APIs to `Session.Store`; they accept patches, not an arbitrary caller-held full snapshot. They read raw current metadata once with its revision, apply only owned fields (including explicit nested config put/delete operations), and compare that exact `mod_revision`. Pure domain validation belongs above Store. There is no new selection sidecar, GenServer, lock service, database, or scheduler.

Every metadata-dependent domain derivation, validation, nested config patch and no-op decision is based on one raw metadata snapshot and its `mod_revision`. The command carries that expected revision into Store; the conditional mutation must compare that exact revision. Store must not refresh the comparison token and apply a patch derived from an older record. If the expected revision no longer matches, return a confirmed conflict. Reconciliation re-reads and re-derives the complete semantic command, including resolution, validation and no-op detection; it never merely reuses the old patch. A no-op is explicitly an observation of the identified snapshot, not an assertion that no later request exists. An opaque snapshot/revision token accompanies the typed patch; this does not make a caller-held full snapshot the write payload.

Proposed interfaces: `metadata_snapshot`, `patch_metadata`, `append_turns_and_patch`, and `replace_turns_and_patch`. Concrete arities are implementation work. Each takes the caller's remaining bounded deadline and returns acknowledged metadata/revision or an explicit result. Confirmed conflicts require re-reading and recomputing the *semantic patch*, never merely replacing the token on a stale full map. Start with no automatic retries; uncertain dispatch outcomes must not be retried or reported as no effect. Shared timestamps are generated for the current patch, not copied from a stale Session.

Before enabling selection mutation, migrate every current metadata writer:

- `Sessions.persist_update/update_meta_field`, stale-status and unsupported-model recovery; creation is create-if-absent, not unconditional replacement.
- `Worker.Config.persist_session` (model, Agent and mode/default-resolution paths).
- `Worker.Boot.reset_transient_status`, `Worker.Persistence.update_session_status`, and `Worker` subagents config update.
- `Agent.Tools.SessionState` plan-mode Agent update.
- `Store.commit_turn/commit_turns`, `append_automation_turn`, and `replace_turns/3` through `Message.persist_list/3`; retain the no-metadata replacement contract of `replace_turns/2`.

Reserve the metadata suffix in generic session-value mutation APIs so they cannot silently bypass the new contract. No production full replacement of an existing metadata record remains. All ordinary changes preserve selection/adoption unless their owning operation explicitly changes those fields. This is necessary because merging *only the new selection field* still loses concurrent title/status/config edits.

Append and metadata patch must be one conditional publication. Turn offset is still owned by the existing Worker; the Store does not acquire scheduling authority. Preserve the existing turn replay/idempotency contract and do not split a turn into partial batches to fit transactions. Atomic transcript replacement can use the existing compared `replace_prefix` API. Conditional append preserving current batch capacity is blocked on the supported delete-free contract tracked in Concord #117; the smaller transaction envelope is not silently acceptable. Existing append admission is 500 total pairs including the metadata pair, not 500 new turns plus metadata; replacement has its separate 501-pair contract. This is an implementation gate, not an assertion that #107 remains open.

## Asynchronous persistence and runtime adoption

1. Native tool execution calls the shared selection domain service within its existing supervised effect. For a live session, the Worker tracks the correlated operation and delegates metadata I/O to a supervised task; it remains responsive. With no Worker, the same service patches the existing record without waking execution. Concurrent writers are fenced by Store, not a caller-local lock.
2. Successful persistence acknowledgements carry their acknowledged metadata revision and operation correlation. The Worker tracks the revision represented by its metadata/selection projection and never replaces that projection with an older acknowledged record. A late older acknowledgement may still complete its own caller with the accurately committed request/result; it cannot overwrite newer live metadata or publish a selection change as current. The tool returns `changed`/`pending`; provider config of the current attempt remains untouched. Persisting a request during tool execution does not dispatch an LLM or start another run. Native attempt observations are independently checked against their actual run/incarnation/attempt identity and pinned selection request ID. Metadata revision ordering must not be used to invent or reorder native attempts.
3. Before a normal native run admission, the existing supervised preparation task reads/resolves the latest observed selection and pins its request ID plus resolved provider/model/config. History compatibility and model-dependent preparation/compaction use that pinned selection. Remove synchronous whole-history preflight from the Worker mailbox path. Concurrent requests after the selection snapshot remain pending for a later eligible boundary; do not promise the latest edit always wins an already preparing run.
4. Pass the pin in trusted ephemeral provider context. The provider adapter observes actual native-issued attempts with their run/incarnation/attempt IDs, while Backplane continues to admit and execute them. Send a correlated observation through SessionAdapter/Worker using a bounded host observation interface; do not create a second executor or infer adoption from options construction alone. Source currently has no such model-adoption projection; it must be implemented and positively verified.
5. Live status can show the observed actual model while durable status still shows the last committed attempt. At the turn persistence boundary, atomically append messages and patch the confirmed adoption projection. Its request ID must match the selected request before pending can clear; a later intent survives the older completion. Ordinary terminal acknowledgement/queued next-turn release continues to wait for the existing persistence ACK.
6. On normal idle shutdown/reopen, restore selection and historical adoption separately. Do not claim the restored last attempt is active. The next admitted run resolves pending override/default and uses it. Existing unsettled-run recovery-required behavior remains; normal restore is not crash-replay acceptance.

### Full reference recovery/compaction boundary

The end-state needs a **native-owned eligibility decision** with no already-published assistant/tool effects being replayed, and a pinned selection identity attached to the adopted provider attempt. It may occur inside the current user turn; it must not happen merely because another HTTP call is about to start. An eligible native boundary resolves the latest persisted request, runs required model-dependent preparation, adopts/pins the selection, then dispatches through the existing adapter. A newer committed request stays pending.

Available-source qualification:

- `ConversationAdapter.stream/2` supplies actual native attempt identity; prompt/stop hooks exist. These enable host resolution/observation but do not themselves certify replay safety or restart an admitted run with new options.
- `Conversation.request_new_context` (`conversation.ex:566,2330`) records a request; after a tool boundary it clears messages, increments the window, checkpoints, and starts the provider. `base_effect_context/4:3012` still reads the original `provider_context`. This is neither a model-stage operation nor reference summarizing compaction. Do not invoke it solely to force a model change.
- `stage_catalog` stages tools, not provider/model state. `status` and host event observation are not atomic ownership/adoption APIs. Restored nonterminal native runs deliberately enter `recovery_required`.

The follow-up bounded qualification inspected public Conversation calls, provider callbacks/request construction, Kernel, Recovery, Context.compaction and published EMBEDDING.md against the official 1.10.57 artifact. No suitable complete safe-boundary model-adoption contract was established. Backplane #154 now tracks the required Feature or identification of an already adequate published route. Provider transport adaptation is already possible; the missing documented contract is native eligibility plus pinned adoption lifecycle. This is not a claim that an advertised API is defective or authorization to implement a host recovery loop. Consume and verify the supported published contract before completing that branch. Do not implement all-HTTP-request switching, cancel/restart orchestration, private state mutation, or synthetic new-context calls as a substitute. Full acceptance remains open while this gate is open.

## Implementation sequence after approval

1. Resolve Backplane #154 and Concord #117 through adequate supported public contracts, adopting official fixes within scope when required. Freeze the selected public behavior and exact affected-file list; no dependent implementation starts behind an unresolved required primitive.
2. Implement the additive model representation and data-only patch/publication interfaces; migrate all metadata writers as one coherent protection boundary. Preserve unrelated working-tree changes and existing capacities.
3. Implement shared selection/default resolution, asynchronous command ACKs, and native tool schema/result revision; connect the existing idle facade and clarify its presentation semantics. Do not retain an obsolete read-only/retry-safe descriptor for a mutating operation. Preserve existing grant routing without expanding policy.
4. Add native attempt observation and ordinary admission/restore adoption. Complete native recovery/compaction integration only through the qualified public interface. Keep slice acceptance separate from whole-reference acceptance.

- Two successful selection requests surrounding a completion: the first attempt's observation/commit cannot consume the second request. Include real native attempt IDs, not seeded adoption metadata. Also deliver two successfully committed metadata ACKs to the Worker in the opposite order and confirm the newer revision remains visible while both callers receive their own accurately committed result. A command derived from an earlier metadata revision must re-derive resolution/no-op after a confirmed conflict rather than attach the newer comparison token to its old patch.
